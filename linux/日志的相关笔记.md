# 日志

- 日志：应用产生的记录
  - `sshd`产生“有人尝试登录”的记录；
  - `nginx`产生“谁访问了哪个界面的”的记录；
  - 你自己写的 Python 程序也可以用 `logging` 模块产生记录



#### 产生日志的应用

1. 系统级服务（最典型） ssh  ,crond,  systemd

2. 网络服务（常见于服务器） web服务器，数据库，邮件服务

3. 安全软件     防火墙，入侵检测系统，审计系统

4. 用户应用程序    自己写的程序

5. 容器和编排工具   docker

## 安全视角下最重要的“应用”日志

| 应用/服务 | 对应日志文件（CentOS 7）        | 典型安全事件             |
| :-------- | :------------------------------ | :----------------------- |
| sshd      | `/var/log/secure`               | 暴力破解、异常登录       |
| nginx     | `/var/log/nginx/access.log`     | Web 扫描、SQL 注入尝试   |
| iptables  | `/var/log/messages`（或自定义） | 端口扫描、DDoS 攻击      |
| auditd    | `/var/log/audit/audit.log`      | 敏感文件被非法读取、提权 |
| cron      | `/var/log/cron`                 | 攻击者添加定时任务后门   |



#### 初步认识

- ✅ 日志文件默认在 `/var/log/` 下
- ✅ 初次没有文件，rsyslog 会在第一次写入时自动创建
- ✅ 具体写进哪个文件，由 rsyslog 的配置规则决定
- ✅ logrotate 负责轮转这些文件，防止磁盘被撑爆



#### 深化认识

**日志管理的三个核心环节**

| 环节               | 你的比喻          | 实际组件                     | 核心动作                                                     |
| :----------------- | :---------------- | :--------------------------- | :----------------------------------------------------------- |
| **生产**           | 流水线上的原材料  | 应用（sshd、nginx、logger…） | 调用 `syslog()` 或写文件，产生原始日志                       |
| **分类**           | 传送带与分拣员    | rsyslog（或 journald）       | 接收日志，根据规则（设施.级别）决定写入哪个文件（`/var/log/secure`、`/var/log/messages` 或自定义文件） |

### logger命令

`logger` 本质上是一个“日志消息发送器”   ，它**不会**自己写任何文件，**不会**创建日志文件，**不会**轮转文件。它只是一个**发送者**。



- `logger` **确实不直接写文件**，它只是把消息发给 **`/dev/log`**。
- 接收 `/dev/log` 的是 **journald**（或内核的 syslog 缓冲区），而不是 rsyslog 直接接收。
- rsyslog 通过 `imjournal` 或 `imuxsock` 从 journald 获取消息，再写入 `/var/log/messages`。



**`logger` 是“日志消息投递员”，它把消息交给系统的日志基础设施（journald + rsyslog），由它们决定最终写入哪个文件。它自己从不直接操作文件。**



## 对你之前的实验意味着什么？

你之前执行 `logger -p authpriv.info "Test"` 后，消息路径是：
`logger` → `/dev/log` → journald → rsyslog（启动后从 journald 读取）→ 根据 `authpriv.*` 规则写入 `/var/log/my-ssh.log`

所以你看到 `/var/log/my-ssh.log` 里有内容，并不是 `logger` 写的，而是 rsyslog 根据规则写的。



### rsyslog规则

### 一，是什么

一句话：规则就是告诉rsyslog**'什么样的日志，送到哪里去'**

每条规则占一行

```
设施.优先级  动作
```

- **设施**：日志的来源分类（如 `authpriv` 认证、`cron` 计划任务、`kern` 内核、`user` 用户级、`local0`~`local7` 自定义）
- **优先级**：严重程度（`debug` < `info` < `notice` < `warning` < `err` < `crit` < `alert` < `emerg`）
- **动作**：通常是写入某个文件（如 `/var/log/my-ssh.log`），也可以是转发到远程服务器、丢弃、执行程序等。

## 二、规则放在哪里？

- 主配置文件：`/etc/rsyslog.conf`（一般不改）
- 自定义碎片文件：`/etc/rsyslog.d/` 目录下，以 `.conf` 结尾，例如 `/etc/rsyslog.d/10-my-auth.conf`。

**推荐做法**：在 `/etc/rsyslog.d/` 里创建自己的配置文件，数字前缀表示加载顺序（如 `10-`、`20-`）。

我们把 **“设施.级别”** 拆成两块来讲，每一块都用生活中的例子类比，然后回到你亲手用过的 `logger -p authpriv.info`。

------

## 一、设施（facility）—— 相当于“部门”

设施就是**日志的“来源部门”**。不同的应用/服务属于不同的部门。

| 设施                | 代表的部门       | 哪些程序会用                             |
| :------------------ | :--------------- | :--------------------------------------- |
| `authpriv`          | 安全认证部       | `sshd`（SSH登录）、`sudo`、`login`       |
| `cron`              | 定时任务部       | `crond`（计划任务）                      |
| `kern`              | 内核部           | 内核自己（硬件错误、网络栈）             |
| `user`              | 用户程序部       | 你自己写的程序（默认）                   |
| `local0` ~ `local7` | 预留的自定义部门 | 随便你用，比如把 Nginx 日志标为 `local0` |

**一句话**：设施就是告诉你“这条日志是哪个部门发出的”。

------

## 二、级别（priority / severity）—— 相当于“紧急程度”

级别就是**这条日志有多严重**。从低到高（越往后越严重）：

| 级别      | 含义     | 什么时候用                                     |
| :-------- | :------- | :--------------------------------------------- |
| `debug`   | 调试信息 | 开发时用来打印变量值                           |
| `info`    | 普通信息 | 正常操作记录（如“用户登录成功”）               |
| `notice`  | 注意     | 正常但重要的事件（如“服务重启”）               |
| `warning` | 警告     | 出了点小问题，但没挂（如“磁盘使用率80%”）      |
| `err`     | 错误     | 发生了错误，但服务还能跑（如“配置文件语法错”） |
| `crit`    | 严重     | 系统快不行了（如“磁盘写失败”）                 |
| `alert`   | 警报     | 需要立即处理（如“数据库连接丢失”）             |
| `emerg`   | 紧急     | 系统崩溃，所有人赶紧跑（如“内核panic”）        |

**一句话**：级别告诉你“这件事有多急/多严重”。

------

## 三、组合起来：设施.级别

规则中的 `设施.级别` 是一个**匹配条件**，意思是：
**“来自某个部门、且紧急程度不低于该级别”** 的日志。

### 例子1：`authpriv.*`

- `*` 代表所有级别（debug 到 emerg）。
- 所以这条规则匹配：**所有来自安全认证部的日志，不管多严重**。

### 例子2：`authpriv.info`

- 匹配：**来自安全认证部，且级别 >= info** 的日志。
- 也就是 info、notice、warning、err … emerg 都会被匹配。
- 但 `debug` 级别不会被匹配（因为 debug < info）。

### 例子3：`cron.err`

- 匹配：**来自定时任务部，且级别 >= err** 的日志（err、crit、alert、emerg）。
- 普通的 info、notice 不匹配。

### 例子4：`*.emerg`

- 匹配：**任何部门，但只限 emerg 级别**（系统最严重的消息）。

## 四、你亲手用过的 `logger -p authpriv.info`

bash

```
logger -p authpriv.info "Test"
```



- `-p` 指定设施和级别。
- 你指定了 **设施=authpriv，级别=info**。

这条消息被 rsyslog 收到后，会去匹配所有的规则。如果你的规则是：

text

```
authpriv.*    /var/log/my-ssh.log
```



那么它匹配，因为 `authpriv.*` 包含 `authpriv.info`（info 是 * 的一部分）。

如果你的规则是：

text

```
authpriv.warning    /var/log/warning.log
```



那么它 **不匹配**，因为 `info` < `warning`（级别不够高）。

## 五、为什么需要理解“设施.级别”？

- **精确分类**：你可以把不同级别的日志分到不同文件。
  例如：`authpriv.err` 写到 `/var/log/auth-errors.log`，只记录严重的认证错误；
  `authpriv.info` 写到 `/var/log/auth-all.log`，记录所有认证日志（包括正常登录）。
- **减少噪音**：生产环境中，`debug` 和 `info` 日志非常多，你可以在 rsyslog 里丢弃它们（不写文件），只保留 `warning` 及以上。

### `设施.级别`称为**选择器**，

### `路径`（例如`/var/log/my-ssh.log`）称为动作



一条完整的rsyslog规则格式就是

```
选择器   动作
```

举例说明

```

```



**动作不一定是文件路径**

还可以是

- 转发到远程：@192.168.1.100：514
- 丢弃：`~`
- 执行程序：|/path/to/script



### 1.为什么叫**“选择器”**？

因为它做了两件事情：

1. 按来源（设施）筛选
2. 按严重程度（级别）筛选

所以它既是来源规定，也是级别过滤





### 2.动作分类：保留VS丢弃

| 类别     | 含义                                                     | 常见动作示例                                                 |
| :------- | :------------------------------------------------------- | :----------------------------------------------------------- |
| **保留** | 把日志留下来（存到某处、转发出去、或交给另一个程序处理） | - 写入文件：`/var/log/secure` - 转发到远程：`@192.168.1.100:514` - 执行程序：`|/usr/local/bin/log-processor` |
| **丢弃** | 不再处理这条日志（忽略它）                               | `~` 或 `stop`（现代语法）                                    |

**保留的“结果”** 不限于转发或执行，写入文件也是最常见的保留方式。你总结的“转发或执行”只是其中一部分，还包括本地存储。

## 3. 补充：动作还可以有更细的控制

- 多个动作：可以写多条规则，同一条日志匹配多个规则，就会执行多个动作（例如既写本地文件又转发远程）。
- 动作前的 `&` 符号（老语法）或直接换行写新规则，都可以实现多重处理。
- 使用 `& stop` 或 `stop` 可以在某个动作后停止继续匹配，避免重复。



### 为什么要转发和执行

## 一、转发（Forwarding）—— 把日志发送到远程服务器

### 语法示例

text

```
*.*    @192.168.1.100:514      # UDP 转发
*.*    @@logserver.example.com:514   # TCP 转发（两个@@）
```



### 为什么需要转发？

| 场景         | 说明                                                         |
| :----------- | :----------------------------------------------------------- |
| **集中管理** | 你有 10 台服务器，不想每台都登录查看日志，可以全部转发到一台中央日志服务器（如 ELK、Splunk），统一存储和分析。 |
| **安全加固** | 攻击者入侵服务器后，可能会清除本地日志（`rm -rf /var/log/`）。但如果日志实时转发到远程，攻击者无法删除远程副本，你仍然可以取证。 |
| **合规要求** | 等保 2.0、PCI-DSS 等要求日志至少保留 180 天，且必须与生产系统隔离。转发到独立的日志服务器满足这一条。 |
| **实时告警** | 中央日志服务器可以实时分析收到的日志，发现 `Failed password` 次数过多立即发送告警。 |

**网络安全角度**：转发是实现“日志不可篡改、集中监控”的基石。

## 二、执行（Executing）—— 把日志作为输入运行外部程序

### 语法示例

text

```
authpriv.*    |/usr/local/bin/alert.sh
```



### 为什么需要执行？

| 场景           | 说明                                                         |
| :------------- | :----------------------------------------------------------- |
| **实时响应**   | 当检测到 `crit` 级别日志（如“磁盘即将满”），立即执行脚本发送邮件或短信。 |
| **自动化封禁** | 解析 `sshd` 的 `Failed password` 日志，提取攻击 IP，调用 `iptables` 或 `fail2ban` 加入黑名单。 |
| **日志结构化** | 把非结构化的日志（如 Nginx 访问日志）通过脚本转换成 JSON，再发到 Elasticsearch。 |
| **自定义存储** | 将日志写入数据库（MySQL、PostgreSQL）而不是文件，方便查询。  |

**网络安全角度**：执行动作可以实现“自动阻断攻击”、“实时报警”，缩短应急响应时间（MTTR）。

------

## 三、对比本地存储（写文件）

| 动作类型   | 优点                               | 缺点                                        |
| :--------- | :--------------------------------- | :------------------------------------------ |
| **写文件** | 简单、可靠、性能高                 | 攻击者可能删除；分散在多台机器难以分析      |
| **转发**   | 集中管理、防篡改、便于关联分析     | 需要额外网络和服务资源；可能丢包（UDP）     |
| **执行**   | 实时处理、高度灵活、可联动其他系统 | 脚本出错可能影响 rsyslog 性能；需要谨慎编写 |



## 总结

- **转发**：解决日志**集中管理、防篡改、合规留存**问题。
- **执行**：解决**自动化响应、实时告警、联动处置**问题。

这两种动作让你的日志系统从“被动存储”升级为“主动防御”的一部分，是网络安全运维中不可或缺的能力。

### ”执行“到底是什么意思？

不是日志在执行，而是rsyslog收到一条日志后，去执行（运行）一个外部程序（比作一个脚本或命令），并且把这条日志的内容作为输入传递给那个程序

## 语法和例子

bash

```
# 把认证相关的错误日志，传给 /usr/local/bin/alert.sh 这个脚本
authpriv.err    |/usr/local/bin/alert.sh
```



竖线 `|` 后面跟的就是要执行的程序路径。rsyslog 会把每一条匹配的日志作为**标准输入**（stdin）传给这个程序。

所以rsyslog的“执行"=触发一个外部程序

**执行”就是让 rsyslog 在收到日志时“顺便跑一个脚本”，从而扩展日志系统的能力**。



什么叫标准输入？

首先认识一下

while read line;

`while read line` 是 Bash 脚本中**逐行读取输入**的标准写法。它的作用是：从标准输入（或管道、文件）中每次读取一行，将这一行的内容赋值给变量 `line`，然后执行循环体内的命令。

## 一、语法分解

bash

```
while read line
do
    # 这里可以处理 $line 变量
    echo "读到: $line"
done
```



- `read line`：读取一行输入，存入变量 `line`。
- `while`：只要 `read` 成功读到一行（即没有遇到文件结尾），就继续循环。
- `do ... done`：循环体。

## 二、工作原理

- `read` 每次从标准输入中取一行（以换行符分隔）。
- 如果成功读取，循环继续；如果读到文件末尾（EOF），循环结束。
- 常用于处理管道传递的多行文本。

### 简单例子

bash

```
echo -e "第1行\n第2行" | while read line; do echo "我读到了: $line"; done
```

输出：

text

```
我读到了: 第1行
我读到了: 第2行
```



## `>` 和 `<<` 的含义

### `>`：输出重定向（创建/覆盖文件）

- **作用**：将命令的标准输出写入到文件，而不是显示在终端。

- **行为**：

  - 如果文件**不存在**，则**创建**该文件。
  - 如果文件**已存在**，则**覆盖**原内容（清空后写入）。

- **示例**：

  bash

  ```
  echo "hello" > file.txt   # 创建 file.txt 并写入 hello
  ```

  

> 注意：`>` 不是只能创建新文件，它也能覆盖已有文件。如果你只想追加内容而不覆盖，用 `>>`。

### `<<`：Here Document（内嵌输入）

- **作用**：将一段多行文本直接作为命令的标准输入，常用于脚本或交互式命令中。

- **语法**：`<< 结束标记`，后面多行内容，最后以单独的 `结束标记` 结束。

- **示例**：

  bash

  ```
  cat > file.txt <<EOF
  第一行
  第二行
  EOF
  ```

  

  这会把 `第一行\n第二行` 写入 `file.txt`。

- **引号的影响**：

  - `<<'EOF'`：内容中的变量（如 `$USER`）和命令替换（如 `$(date)`）**不会**被展开，原样写入。
  - `<<EOF`（无引号）：会展开变量和命令替换。

**总结**：

- `>` 是输出重定向，创建或覆盖文件。
- `<<` 是 Here Document 的起始，用于提供多行输入。

你之前看到的 `cat > file <<'EOF'` 组合就是：**将 Here Document 提供的内容通过 `cat` 写入到文件中**。



**`echo` 的输出可以通过 `|` 管道作为另一个命令的输入**



```
echo "Hello" | wc -c
```



**不同的日志可以被 rsyslog 规则分发到不同的文件或不同的处理方式：**

1. **写入文件（存储记录）**
   最常见的动作：`authpriv.* /var/log/secure`
   作用：将日志追加到指定文件中，供后续查看、分析、轮转。
2. **发送给外部程序（执行文件）**
   动作：`local0.* |/usr/local/bin/log_receiver.sh`
   作用：将每一条匹配的日志作为标准输入传递给外部脚本，由脚本进行实时处理（如告警、封禁IP、写数据库等）。

**两者可以同时使用**（写多条规则，或使用 `&` 动作），例如：

text

```
authpriv.*    /var/log/secure
authpriv.*    |/usr/local/bin/alert.sh
```



这样日志既存文件，又触发脚本。

**总结**：日志文件“仅仅存储记录”是基础功能；“发送到别的执行文件”是扩展功能，用于自动化响应。你之前实验中的 `log_receiver.sh` 正是后者。
